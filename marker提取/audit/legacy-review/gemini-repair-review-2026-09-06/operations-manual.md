## 1. 目标、边界与执行顺序

### 1.1 本阶段目标

以现有`our_markers.xlsx`为主体，筛查并纠正错误关系、移出已确认无效记录、清理重复，形成相对完善、可追溯且核验边界明确的终版总表。已有修补候选和明显遗漏作为次要工作处理，不以新增数量或补漏穷尽作为完成指标。

主要工作是：

1. 对现有总表建立全量记录覆盖的风险筛查清单，优先核验错配、物种、实体、方向、证据误引及重复问题；全量风险筛查不等于逐条重新提取或逐材料重读。
2. 结合953条基线回填及历史审查发现定位风险，确认真实错误后纠正或移出，不将回填误当独立补核。
3. 将原62条候选和原28项未决关联到现有记录，涉及现有总表准确性的项目优先处理，其余按定向核验及停止条件收尾。PRR4已有可纳入证据，Glb1错误测量实体已撤销，其余26项不得默认全部需要持续追查。
4. 复查28条context_only和121条excluded的分类理由，优先处理不当排除风险，证据明确时恢复；不借此展开全面补漏。
5. 分批更新两份正式表，保存变更前后值、证据和验证结果；终版验收以已知高风险错误完成处置为核心。

### 1.2 不在本阶段自动展开的工作

- 不重新从零提取全部43篇论文。
- 不开展前两轮20篇的新一轮全面补漏。
- 不以重写Gemini总结报告代替证据核查。
- 不恢复已停用的旧自动提取、批量恢复管线。
- 不把现有总表或历史裁决视为永远正确；发现有直接证据支持的基线错误时，另立纠错记录处理。

核查一个面板时如发现紧邻的、明确且遗漏的marker，可以另建候选并登记为“本阶段追加发现”；这不是扩大到全文重提取。追加候选不能悄悄混入原62条完成率。

### 1.3 推荐执行顺序

| 阶段 | 主要任务 | 责任方 | 阶段产出 |
|---|---|---|---|
| A | 固定基线、建立统一台账 | Luna准备，Astra审查范围 | 基线快照、候选清单、关联关系 |
| D优先 | 现有总表全量风险筛查，核验953条映射风险及历史错误；定向复查不当排除 | Gemini首筛→Luna复筛→Astra裁决 | 风险覆盖清单、纠错与移出清单 |
| B | 核验62条候选，优先处理涉及现有总表纠错的记录 | Gemini首筛→Luna复筛→Astra裁决 | 逐条裁决、有限证据请求 |
| C按需 | 对影响裁决的具体缺口补核，接续原28项 | Gemini取证→Luna复核→Astra裁决 | 材料清单、证据记录、停止原因 |

### 1.4 定向补核的范围与停止条件

- 每项先复用历史已核验证据，再查看原引文、相关面板及明确指向的正文/附件位置；同一材料可合并核查多个已有问题。
- 每项按两轮筛查加最终裁决完成一个定向核验周期；只有出现新的、具体的证据位置线索且会改变裁决时，才追加补件。不反复全文搜索、不反复派发相同缺口、不重跑提取。停止取证不免除Luna复核和Astra裁决。
- 指定材料已查仍不能裁定，或附件不可获取/内容不可读时，记录已查范围、剩余缺口和停止原因。未入库候选保持unresolved，不新增，不阻塞终版。
- 涉及现有正式记录的关键疑点不能仅登记待办后照常当作已确认记录。须核对历史独立证据：足够支持则说明保留依据；有明确错误则纠正或移出；关键关系仍无法确认则保留原记录及历史，将其置于可追溯的未决隔离清单，不计入已确认marker集合。隔离不等于exclude或物理删除。
- 无新线索的未决隔离项可以停止追查，但必须在终版交付中单独披露；不得宣称其关系已解决。
- 顺带发现的明显遗漏，证据现成且符合政策时补充；需要大范围探索才能证实的，登记候选后停止，不扩大本阶段范围。

## 2. 必须遵守的判定口径

唯一范围政策是 [MARKER_POLICY.md](../../MARKER_POLICY.md)。本手册补充执行方法，不替换该政策。

### 2.1 正式纳入条件

候选至少具备以下一种可靠证据，并且gene–cell关系、物种、实体及来源可以确定：

| 证据类型 | 可接受情况 | 不足以支持的情况 |
|---|---|---|
| author_declared | 作者直接建立该基因与该细胞/状态的marker关系 | 只说某基因参与通路或机制 |
| annotation_marker | 作者实际用于识别、注释、命名、分选、门控或身份验证 | 仅出现在抗体清单或方法名中 |
| figure_labeled | 图或图注明确呈现可读、用途明确的gene–cell对应 | 仅凭点大、颜色深或邻近位置推断 |
| supplementary_marker | 实际查看的补充材料明确列为marker或注释基因 | 未查看的补充表，或没有注释用途的普通DEG表 |

### 2.2 不得额外添加的门槛

不得仅因以下原因删除或降级真实marker：

- 不属于PNS或L1–L4。
- 不属于论文主打的组织、物种或细胞群。
- 是经典marker、共享表达、不具排他特异性。
- 不是论文“新发现”。
- 证据来自蛋白染色、门控或定位，而非RNA点图。

同样不能反过来把所有高表达、DEG、免疫染色或图中基因自动收录。必须证明本文建立或实际使用了该关系。

### 2.3 四类语义裁决

| semantic_decision | 含义 | 后续处理 |
|---|---|---|
| include | 符合正式证据要求 | 再判断已有、新增或纠错 |
| context_only | 有相关材料，但只支持富集、功能、模型或纯外部引用 | 保存上下文，不入正式marker表 |
| exclude | 明确错误配对、无效实体、重复污染等 | 保存具体被否定的记录及理由 |
| unresolved | 材料、实体、物种或对应关系不足以裁定 | 保留具体缺口与下一步 |

“原图不支持这条引文”并不等于“全文不存在这个关系”。应分别登记引文动作与关系结论。

## 4. 两轮筛查与最终裁决的模型分工

本节是执行角色的统一解释：下文“Gemini”指第一轮Gemini 3.8 Flash high；“Codex”是Luna和Astra的统称，其中接收、复核、台账与暂存由GPT-5.6 Luna max承担，“最终裁决”“确定semantic_decision”“批准发布”仅由GPT-6 Astra medium承担。历史文件中的Codex/Gemini名称保持原义，不改写历史归属。

### 4.0 三层执行协议

| 层次 | 模型 | 主要任务 | 必须交付 | 权限边界 |
|---|---|---|---|---|
| 第一轮筛查 | Gemini 3.8 Flash high | 按已有记录逐项筛错；承担大部分材料定位、原图读取、图注核对、表格定位，提出可疑配对与字段问题 | 每条首筛结论、证据位置、全图与细节图、风险类型、未决缺口 | 仅提建议，不修改正式表，不作最终排除 |
| 第二轮筛查 | GPT-5.6 Luna max | 覆盖全部首筛记录；独立核对证据用途、物种、实体、细胞粒度、方向、映射和去重，识别首轮漏报及误报 | 每条复筛意见、实际核查范围、两轮分歧、建议动作、拟议change_set及验证结果 | 不将Gemini结论直接复制为已验证，不批准自己的变更 |
| 最终审查与裁决 | GPT-6 Astra medium | 审查全部拟议变更、高风险、未决及分歧；核验决定性原始证据；对保留项分层抽查，批准批次并验收终版 | 最终decisions、逐项裁决理由、批次审批、抽查记录及终版验收 | 唯一最终裁决角色；模型投票或两轮一致不能替代证据 |

执行单位优先按论文及共享面板分批。每批必须先完成首筛、再复筛、再裁决；不同批次可流水推进，但不同时修改同一记录。三层流程不是三次全文提取。

**首轮覆盖**：以当前总表全部marker_id建立清单；复用可信历史定位，检查已存在记录的正确性。来源不明或未实际查看应如实标注，不能自动写通过。953条回填不是全表覆盖的替代品。

**第二轮独立性**：Luna逐条核对首筛结果及对应证据。凡结论依赖图像，须实际查看决定性面板、标签与图注，不能只读Gemini描述；文字或表格证据直接核对原位置。可以复用截图、同一面板和已核验材料，避免重复下载与渲染。无法读清或出现分歧时交由Astra查看原始材料，不以模型名称推定谁正确。

**最终审查范围**：Astra逐项审查所有add、update、merge_duplicate、remove、move_to_unresolved及所有高风险、未决、两轮分歧项。对两轮一致且低风险的no_change项，每篇论文抽查至少5条，不足5条则全查，兼顾图像、文字、表格等实际存在的证据类型；记录抽查ID与选择理由。发现关键关系错误时，扩大复查至该论文同面板/同错误类型全部关联记录；再次发现同类错误则退回该论文全部保留项复筛。抽查不应被报告为Astra逐条重读全表。

更多读图工作分配给Gemini是工作安排，不是准确度保证。首轮输出一律作为待复核证据；Luna意见也须接受最终审查。无可靠证据时保留不确定性，不为达成一致补写内容。

### 4.1 Codex负责

- 解释并应用项目纳入政策。
- 区分相同关系、纠错关联、跨物种关系与独立新增。
- 阅读原文/原图，对每项作最终语义裁决。
- 核验Gemini交付的截图、引文和表格定位。
- 决定正式表新增、修改、去重或移出。
- 维护统一裁决台账，更新两份正式表并验证。

### 4.2 Gemini适合负责

- 根据明确论文和材料名称获取附件。
- 核对真实文件名、页数、标题、DOI及其来源。
- 按指定面板截图，按指定基因检索候选位置。
- 在补充表中定位sheet、行列与注释说明。
- 整理逐字引文、图像观察和材料缺口。
- 执行字段完整性、文件存在性、页码范围及数量一致性检查。

### 4.3 写入责任

Gemini只写入分配给它的任务目录。不得编辑正式Excel、历史JSON或Codex最终裁决。Codex读取其交付后，将可用内容写入自己的统一台账。

Luna维护接收副本、复筛意见和拟议变更，只在staged中预演；Astra写入最终裁决并批准绑定基线哈希与change_set哈希的批次。Luna可按该已批准批次执行发布，内容或基线变化须回到Astra重新审查。这里的模型审批是内部质量步骤，不是每批重新请求用户许可。

同一条记录不让两个执行方同时修改。并行以论文、面板或明确任务包划分；共享材料可以引用同一个文件哈希，避免重复下载和互相覆盖。

一般已授权的整理、核验和聚焦修复直接执行，不为每个批次重复请求用户批准。遇到无法推断的业务政策变化、权限限制或可能覆盖他人新修改时，再明确说明问题。

## 6. 统一台账的数据结构

### 6.1 ID原则

每个逻辑对象使用自己的ID，不混用作者cluster、Gemini记录号和总表marker_id。

| 字段 | 含义 |
|---|---|
| review_id | Codex给待审记录分配的稳定ID |
| paper_id | 规范论文ID |
| source_record_refs | 历史记录引用数组：版本、文件、类别、record_id或数组下标 |
| original_record_ids | 原提取记录ID，允许为空或多个 |
| repair_record_id | 修补记录ID；必须连同版本解释 |
| baseline_marker_ids | 当前总表关联ID，允许多个 |
| author_cluster_id | 作者实际cluster编号；没有就null |
| evidence_ids | 支持或反驳该关系的证据引用 |
| decision_id | 最终裁决记录ID |

如果历史记录缺record_id，不要填空字符串当唯一键。使用`source_version + file + category + array_index`保留原位置，再分配独立review_id。

### 6.2 候选关系字段

`records.json`每条至少包括：

| 字段 | 要求 |
|---|---|
| marker_original | 原始材料中的实体写法，不被标准符号覆盖 |
| marker | 可唯一确定的标准符号；不能确定则null |
| normalization_basis | 标准化依据与实际查验来源；未核实不写verified |
| species | 来自样本/实验，不能按大小写判断 |
| organ_or_tissue | 具体组织，未知如实保留 |
| cell_type_original | 作者原始细胞标签 |
| cell_type | 当前采用的细胞名称 |
| subtype | 亚群、状态或作者标签；不要丢失关键粒度 |
| experimental_context | 发育阶段、疾病、模型、处理条件等 |
| measurement_type | RNA、protein、chromatin_accessibility等，不能统一默认RNA |
| entity_detail | 蛋白异构体、转录本、报告系统或其他实体限定 |
| marker_direction | positive / negative / low / unknown |
| gate_definition | 完整组合门控；不适用则null |
| four_layer_category | L1 / L2 / L3 / L4 / outside / unknown |
| candidate_origin | 原62项、原28项、分类复查或本阶段追加发现 |

未知信息使用null或明确的unknown枚举，不用“无”“待填”“...”冒充有效数据。示例或模板不得混入生产台账。

### 6.3 三种状态必须分开

| 状态层 | 建议字段 | 示例值 |
|---|---|---|
| 工作进度 | review_status | queued / locating_evidence / ready_for_review / reviewed |
| 语义裁决 | semantic_decision | include / context_only / exclude / unresolved |
| 入库动作 | table_action | no_change / add / update / merge_duplicate / remove / move_to_unresolved / hold |

例如“有证据、已存在”的记录为`reviewed + include + no_change`；“关系不明”是`reviewed + unresolved + hold`。reviewed只表示本次核验工作已做，不等于证据支持纳入。

未入库候选使用unresolved + hold。已有正式记录经Astra裁决需隔离时使用unresolved + move_to_unresolved：从已确认markers集合转存至工作簿独立未决sheet，保留原marker_id、全部原字段、证据及裁决历史，并同步排除出已确认按细胞汇总。先检查现有审计sheet能否承载；不能时新建明确命名的未决sheet，不覆盖原有sheet。此动作不是exclude，也不物理删除记录。

两轮筛查分别保存review_id、baseline_marker_ids、实际model与reasoning_effort、轮次、建议结论、风险类型、evidence_ids、实际核查范围、未查看范围、缺口及停止原因。第二轮另存与首轮的一致/分歧及理由。final_review记录Astra实际配置、最终decision_id、抽查范围、批次审批及获批change_set哈希。三层记录分开保存，禁止覆盖前轮结论；未完成第二轮不能计为两轮通过。

### 6.4 映射类型

| mapping_type | 使用条件 |
|---|---|
| baseline_backfill | 从基线重述，未新增独立核验 |
| same_relation_verified | 物种、细胞/亚群、实体、方向、必要条件均核准为同关系 |
| same_gene_candidate_link | 仅同基因或可能相关，尚待关系核验 |
| correction_of | 明确指出原记录哪个字段错误，保存前后值 |
| independent_new_candidate | 作为独立候选提出；不保证是总表新增 |
| rejected_link | 原先的关联错误，例如跨物种强连 |

同关系的必要判定维度：

```text
论文 + 物种 + 作者细胞/亚群 + 基因/测量实体
+ 方向 + 必要实验条件 + 必要门控限定
```

这是一套语义核验维度，不是把所有字符串拼起来就能自动去重的算法。名称不同可能同义，名称相同也可能来自不同阶段或不同实体。

### 6.5 引文动作与关系状态

`citation_action`独立记录`retained / corrected / withdrawn / pending`。

实际例子：

| 项目 | citation_action | semantic_decision | 理由 |
|---|---|---|---|
| eLife CALCA/CHGA原Fig.1引文 | withdrawn | unresolved | 所引面板不支持，但未证明全文无其他证据 |
| iPain Glb1酶活转表达 | withdrawn | exclude | 该申报记录混淆测量实体 |
| PRR4蛋白识别证据 | retained | include | 按实际蛋白证据记录，不改写为RNA |

### 6.6 证据记录字段

`evidence.json`至少保存：

- `evidence_id`、`paper_id`、`material_id`、`file_sha256`。
- `pdf_page`：从1开始的物理页；`printed_page`单独记录。
- `figure_panel`，或`sheet_name / row_numbers / column_names`。
- `evidence_mode`：`text_quote / visual_observation / table_reading`。
- `verbatim_quote`：只有逐字文本才填；观察类可以为null。
- `visual_observation`：标签、行列、方向、图例及对应依据。
- `source_context`：必要的上下文，不把自己的解释冒充引文。
- `supports_review_ids`、`contradicts_review_ids`。
- `verification_status`、`verified_by`、`verified_at`。
- `full_image_path`、`detail_image_path`或表格定位。

为提高可追溯性，建议路径以项目相对路径保存，并附项目根；给用户的文件链接使用可点击绝对路径。

### 6.7 决策记录字段

`decisions.json`保存追加式决策历史：

- decision_id、review_id、decision_version、supersedes_decision_id。
- semantic_decision、table_action、evidence_ids。
- decision_reason、remaining_gap、needed_to_resolve。
- baseline_marker_ids、before_values、after_values。
- reviewer、decided_at、batch_id。

发现错误时追加新裁决并注明替代关系，不覆盖掉之前的判断。程序可以维护“当前生效决策”视图，但历史记录仍应保留。

### 8.1 论文顺序与检查重点

| 1 | DOI_10.7554_elife.62522 | 23 | Fig.1B/D，RNA与可及性、配对与亚群 |

### 8.2 每条记录的标准操作

1. **读原记录和修补记录。** 对比基因、物种、细胞、实体、方向、来源，不只看marker字段。
2. **查当前总表候选对应。** 先按paper_id和基因缩小范围，再核对其他维度，保留一对多候选。
3. **确认论文身份。** PDF首页、DOI与清单对应；来源文件必须存在且属于该论文。
4. **打开所引材料。** 文本定位后查看必要原图；截图用于辅助，不替代原PDF身份校验。
5. **判断证据用途。** 明确是在注释细胞，还是仅表达、功能、DEG或模型结果。
6. **核对实体与方向。** 蛋白不变成RNA，low不变成negative，活性不变成转录本。
7. **保留作者粒度。** 不自动合并或拆分联合群，不把状态亚群泛化为正常细胞。
8. **作语义裁决。** 保存支持证据、反证及理由。
9. **决定入库动作。** include后仍需判断no_change、update或add；不直接新增。
10. **记录下一步。** 不能裁定时写具体缺口并下发证据请求，不只写“待核”。

#### iPain

- Calca/Mrgprd/Piezo2等没有在当前指定面板找到直接标签时，继续定位其他本文材料；不能据此声称全文无该关系。

## 10. Codex接收Gemini交付的验收流程

每次交付分三层验收，分别报告，不能合并成一个PASS。

### 第一层：机械验收

- 文件、task_id、paper_id、review_id齐全。

## 11. 阶段D：分类复查与基线字段保护

### 11.0 现有总表筛错主线

以实际发布前基线全部marker_id建立baseline_risk_coverage，不仅覆盖953条回填。逐条关联两轮记录、历史证据、风险类别及最终处理；无风险标记只说明筛查范围内未发现问题，不代表重新穷尽论文。

优先级为：已确认/疑似错误关系与物种、实体、方向问题→证据误引及不可追溯→错误合并与重复→其他字段风险→已有补充候选与明显遗漏。历史34、44、361等差异数仅用于定位，不能直接当成错误数或删除清单。

发现风险须按第4节完成两轮筛查和最终裁决，并按第1.4节停止取证或隔离。对28条context_only、121条excluded完成分类理由筛查；存在不当门槛或明确反证的项再定向查证，不逐篇重新寻找所有遗漏。

### 11.1 context_only与excluded的复查

首先按旧理由筛选高风险记录：

```text
不特异 / 泛表达 / 常识marker / 非新发现 / 非免疫
只有IHC / 非PNS / 缺乏排他性 / 总表已经排除
```

这些关键词只用于找复查优先级，不是自动恢复规则。

每项操作：

1. 阅读旧理由，定位其否定的是引文、实体、细胞配对还是用途。
2. 查看实际证据，判断是否应用了项目没有的门槛。
3. 有正式证据则include；仅功能/富集则context_only。
4. 证据不足则unresolved，不把旧exclude原样当新裁决。
5. 确认错误则exclude，并指出具体错误范围。

组合基因条目如必须拆分，保留父记录、拆分原因及每个子记录的独立证据。不得把一条包含12个基因的上下文描述直接批量变成12条正式记录。

### 11.2 953条基线回填的复查

这些记录默认作为已有基线参考，不自动重新发布。重点复查：

- same_gene_candidate_link被误当same_relation的情况。
- 跨物种关联及基因大小写导致的错误标准化。
- 原始实体被标准符号覆盖的34条差异。
- 空four_layer_category被默认outside的44条差异。
- 固定页码、统一RNA测量、统一验证方法和伪text_quote。

注意：34和44是此前识别的字段差异数，不是独立记录总数，也不意味着每项已经完成语义确认。

### 11.3 不从repair覆盖基线

同一marker_id关联成功，只说明该ID存在。写入前仍需验证：

- paper_id属于同一论文。
- 基因、物种、细胞及实验条件一致。
- 新证据确实比现有字段更准确。
- 字段变化有直接证据，不是模板默认值。

原有正确记录可以no_change；存在真实基线错误才update。默认不整体替换一篇论文的全部行。

## 12. 阶段E：分批入库

### 12.1 入库前门槛

一条记录允许进入change_set的条件：

- semantic_decision已经由Codex确定。
- 有已核验的直接证据或明确的排除依据。
- 所有会影响关系唯一性的字段已处理。
- baseline_marker_ids已确认，或明确不存在可匹配记录。
- before_values与当前正式表一致。
- 不依赖仍未获得的材料。

如果一条记录只差非关键备注，不必阻塞整批；未入库候选缺物种、实体或关系对应时必须hold。已有正式记录存在同类关键缺口时，按第1.4及6.3节由Astra判断保留依据或批准move_to_unresolved，不能通过hold让已确认集合中的关键疑点无人处置。

### 12.2 生成change_set.json

每项变更记录：

| 字段 | 内容 |
|---|---|
| batch_id | 所属批次 |
| decision_id / review_id | 追溯裁决 |
| operation | add / update / merge_duplicate / remove / move_to_unresolved |
| marker_id | 已有ID或本批分配的新ID |
| before_values | 旧值；新增时为空 |
| after_values | 新值；移出时明确归档去向 |
| evidence_ids | 直接支持变更的证据 |
| reason | 为什么修改 |
| expected_baseline_sha256 | 应用此变更所依据的正式文件哈希 |

marker_id应检查所有已使用ID及历史审计引用后分配，不使用“当前行数+1”。被移出或合并的ID不复用。

### 12.3 预演与暂存

1. 在staged目录对基线副本应用change_set。
2. 只写授权字段，保留工作簿原有sheet、表格对象和审计历史。
3. 新增来源、引文、方法和分类按实际证据填写。
4. 重新生成按细胞汇总表，沿用现有分组规则，不临时发明新的细胞聚合口径。
5. 使用项目现有可用脚本前先读其实现，确认不会重跑旧恢复逻辑或覆盖历史审计。
6. 按当前会话有效的spreadsheets技能选择作者工具，并完成要求的可视化验证。

### 12.4 数量对账

正式记录数应满足：

```text
发布后已确认行数 = 发布前已确认行数 + 实际新增行 - 明确排除移出行 - 合并时移除的重复行 - 转入未决隔离行
```

普通字段update不改变行数。一个候选可能对应多条已有关系；候选数不等于新增行数。必须分别报告候选裁决数量和实际表格变更数量。

未决隔离行单独对账，确认全部原值与ID仍可追溯，且没有计入已确认汇总。move_to_unresolved必须有Astra裁决；hold本身不改变现有工作簿。

### 12.5 发布前验证清单

#### 数据与证据

- [ ] change_set每项均可追溯decision_id。
- [ ] 两轮筛查记录齐全，Astra最终裁决及批次审批覆盖全部变更，审批与当前change_set、基线哈希一致。
- [ ] 未决隔离记录完整保留，与已确认marker集合及按细胞汇总明确分开。
- [ ] 新ID唯一，旧ID未误复用。
- [ ] 物种、实体、方向、细胞粒度已核对。
- [ ] 没有将缺失信息默认成positive、RNA或outside。
- [ ] 引文与来源文件对应，页码/行列可以复查。
- [ ] no_change和hold未被误写入。

#### 工作簿完整性

- [ ] markers表数据行数对账通过。
- [ ] 无关论文和无关记录逐值保持不变。
- [ ] 既有审计记录保留，新审计按约定追加。
- [ ] 筛选、Excel表范围、格式、冻结窗格和数据验证仍正确。
- [ ] 汇总表按相同规则从最终markers生成。
- [ ] 公式和显示结果没有新增错误。
- [ ] 抽查新增/修改行及汇总视图，长文本可读，没有截断或错位。

#### 并发与基线

- [ ] 发布前重新计算正式表哈希，仍等于本批expected_baseline。
- [ ] 没有其他进程同时编辑两个正式文件。
- [ ] 暂存文件可以重新打开，备份可以读取。

验证失败时修复暂存版本并重验受影响部分，不为了“全绿”删除真实警告或跳过比较。

### 12.6 正式发布

1. 写入发布状态`publishing`，记录两份旧文件和两份暂存文件哈希。
2. 发布经验证的两份文件。
3. 立即重新打开并校验哈希、行数及关键sheet。
4. 两份都完成后写入`published`及时间。
5. 更新PROGRESS.md和当前基线。

两个Excel文件的替换不是天然原子操作。若第二份写入失败，不能宣称发布完成；按下面恢复流程处理。

### 12.7 失败恢复

- 暂存阶段失败：正式表不变，保留错误日志，修复暂存文件。
- 正式表被Excel或同步程序锁定：记录原因，不强行结束用户进程；解决占用后重新核基线再发布。
- 发布中途失败：先记录实际已写入的文件与哈希，确认没有其他新修改；在该条件下恢复本批两份快照，或完成剩余文件使其一致。
- 若发现其他人的新修改：停止覆盖，保留本批change_set，基于新基线重新对照。
- 不使用git reset、删除历史目录或批量恢复旧分支来替代定向回滚。

## 13. 可使用的定位命令与注意事项

以下命令为示例，执行前确认实际路径和已安装工具；本手册不会创建这些运行环境。

### 13.1 检索材料

```powershell
rg --files 'marker提取/pdf'
rg -n -i 'NRXN|CDH19|XKR4' 'marker提取/review_md/DOI_10.1016_j.isci.2024.111628.md'
```

检索无命中只说明当前文本层没有匹配，不证明图像或补充文件不存在该基因。将检索结果当定位线索，不直接作排除依据。

### 13.2 PDF转Markdown

读取新提供的非Markdown文档时按markitdown技能处理；图像内容仍需实际查看。

```powershell
markitdown '<实际PDF路径>' -o '<任务目录中的转换后md路径>'
```

已有可信转换文本可用于检索，不为每次查看重复转换全篇。遇到错误字层、复杂点图或扫描件时，用原PDF和图像核验。

### 13.3 渲染真实图页

已核实iPain Fig.1在PDF第3页，渲染示例：

```powershell
pdftoppm -f 3 -l 3 -r 180 -singlefile -png '<实际iPain PDF路径>' '<任务目录>/ipain-p003'
```

渲染后必须打开PNG验证页面确为目标图。图像清晰但内容错页仍不合格。

### 13.4 写入前哈希检查

```powershell
Get-FileHash -LiteralPath '<正式总表绝对路径>','<正式汇总表绝对路径>' -Algorithm SHA256
```

哈希变化需要解释，不自动视为损坏。发布自己的合法修改后，应保存新的哈希供下批使用。
